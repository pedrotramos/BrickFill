# Architecture

## Goal

Complete a retailer's product catalog with content and attributes that carry **verifiable evidence**:
- sources are discovered on the web and extracted with screenshots;
- the retailer's editorial and catalog rules are applied by deterministic code;
- the result is reviewed in a governed Databricks App, with search, editing, manual evidence and an audit trail;
- only approved products are published.

## Flow

1. **Input: the canonical contract.**
   - An adapter maps the retailer's tables to three documented views: `v_products`, `v_attributes` and
     `v_attribute_options` ([data contract](data-contract.md)).
   - The **Source contract** job creates the views with column comments and validates keys, nullability, GTINs and
     enums (results in `contract_check`).
   - The `prepare` task re-checks the schema and normalizes the views into `product_input`, `attribute_definition`
     and `attribute_allowed_value`. Attributes are scoped by `subcategory_id`.
2. **Settings.**
   - Before selecting the batch, the job reads the app's Settings from Lakebase: global and per department, category
     and subcategory.
   - It resolves the content language, catalog language, editorial profile, market and overrides of each product
     ([configuration](configuration.md)).
   - The snapshot is stored in `enrichment_run.settings_json`.
3. **Batch selection.** The job runs on `enrichment_cron` (in `timezone_id`) and picks products never enriched,
   grouped by category and subcategory.
   - The batch is reviewers × products per reviewer (`enrichment_reviewers`, `enrichment_products_per_reviewer`)
     minus the products still awaiting review: enriched products whose latest result has no `APPROVED` or
     `REJECTED` decision in `brickfill_app.product_review` (the app's review queue, with the same rule).
   - With the queue full, the run ends before calling the model.
   - The `ean` parameter forces a list of GTINs, for reprocessing.
4. **Source discovery (Firecrawl search).** Two queries per product go to the `firecrawl_search` tool of the
   Firecrawl MCP server: the GTIN alone, and the title words with the GTIN.
   - With a market, the search is localized (`location`/`country`) when the tool's schema supports it.
   - Candidate URLs are canonicalized and ranked by GTIN and product name in the URL, brand, and source type. The
     market's marketplaces are deprioritized and social networks go last.
   - `use_native_web_search: "true"` sends the queries to `system.ai.web_search` instead (not available on Azure).
   - A search result is only used for discovery and never becomes evidence.
5. **Research by the agent.**
   - **Pages:** the model receives the pre-extracted pages as markdown (up to 30,000 characters each). It has two
     minimal tools for what is missing: scrape a URL, and search (10 web results), for at most three rounds.
   - **Facts first:** it writes facts cited to extracted pages, then the catalog content from those facts only, in
     the content language. It returns only the attributes it found; the code completes the rest as missing.
   - **Prompt:** built from the profile, locale and market (`src/brickfill/prompt.py`). It depends only on those
     three, so prompt caching works across a batch; per-category rules go in the user message.
   - **Untrusted content:** pages and tool results are wrapped in `<external_page>` tags, and instructions inside
     them are ignored.
   - **Errors and compatibility:**
     - pages answering HTTP 4xx/5xx reach the model as one line and are never citable;
     - endpoints that only accept tools through the Responses API are called through it automatically;
     - a minimal call checks the endpoint before the first product, so an incompatible model fails before spending
       Firecrawl credits.
   - **Cost tracking:** tokens, model calls and Firecrawl credits are recorded in `research_trace`.
6. **Concurrency.**
   - `concurrency` products are researched at once.
   - All Firecrawl requests of a run share `firecrawl_concurrency` slots (the plan's limit).
   - A 429 is retried with backoff.
7. **Visual evidence.** See [Visual evidence](#visual-evidence).
8. **Deterministic validation** (`quality.py`, `postprocess.py`).
   - Metadata generated by code (retrieval time, run ids, providers) overwrites anything the model returns.
   - The rules check:
     - lengths and required brand from the profile;
     - the GTIN check digit and packaging-level GTINs, with logistic and unit terms from the locale packs;
     - exact vocabularies, the source policy and cross-field consistency;
     - promotional terms, generic values and emojis;
     - per-category required facts and image size.
   - Every issue is stored as a code with parameters (`validation_issue.params_json`), so the app shows it in the
     reader's language.
   - A value outside the vocabulary, but with evidence and confidence ≥ 0.8, is published as pre-approved and flagged
     for review.
9. **Write.** The agent's raw output and the validations are kept immutable in Delta. `product_enrichment` is written
   last: it is the marker that publishes the run. The `load_lakebase` task copies the run's products to Lakebase.
10. **Review in the app.**
    - **Reading:** the Databricks App serves every screen from Lakebase: the synced `brickfill_serving.products`
      table and the `enrichment` schema. It never queries a SQL warehouse.
    - **Storage:** reviews, edits, manual evidence, settings and audit live in Lakebase (`brickfill_app`).
    - **Evidence on edits:** every edit requires its own evidence (URL and excerpt, or a screenshot). Reviewers can
      also attach evidence to an AI value.
    - **Upload storage:** uploads go to a dedicated Volume, the only one the app can write, under a server-generated,
      hash-addressed path. The AI evidence Volume is read-only for the app.
    - **Identity:** the author of every change is the user authenticated by Databricks Apps (`X-Forwarded-Email`,
      `X-Forwarded-User`). Without that identity, the app refuses the write; nothing is attributed to its service
      principal.
    - **Concurrency:** writes to the same product (decision, edits, evidence) or settings scope run in a
      transaction under a Postgres advisory lock.
      - A partial unique index allows one active edit per product and attribute.
      - Settings use optimistic versioning: a stale save gets HTTP 409.
    - **Decisions hold for one result.** An approval or rejection records the enrichment run it was made on
      (`product_review.run_id`) and is refused (HTTP 409) when the product changed since the page loaded: a new run,
      or an edit or evidence saved meanwhile. A product enriched again goes back to the review queue, and a failed
      run (no content) can be rejected but not approved.
      - Saving or removing an edit or an evidence reopens an approval (`IN_REVIEW`, audit event `REVIEW_REOPENED`),
        so an approval always covers the current edits.
      - Manual evidence of an AI value records its run too, and is shown and published only with that run.
      - Decisions and evidence saved before the run was recorded hold when they are not older than the result.
11. **Publication.** The app never writes to Delta. The **Publish approved** job reads decisions and edits from
    Lakebase and MERGEs into the destination table (`enriched_products_approved`, keyed by `gtin`, with
    `product_id`). The merged view of each approved product is the approved AI result plus active edits, with the
    source and evidence of every value. An attribute the AI marked as not applicable is published when a reviewer
    edited it.
    - **Removal:** products rejected or set back to pending leave on the next run. A reopened approval
      (`IN_REVIEW`, after an edit or evidence changed the product) keeps the last approved version published until a
      reviewer approves the current content.
    - **No publishable result:** an approved product whose current result is not the approved one (enriched again
      after the approval, a failed run) or that has no catalog row keeps its last published version until a reviewer
      approves the current result.
    - **Empty read:** if no approval is read and the destination has rows, the job fails without changing it.
12. **Operations.**
    - In production, every job runs as a dedicated service principal.
    - All resources carry the same FinOps tags and serverless budget policy.
    - The platform bundle owns the Lakebase project (all targets) and, in production, the jobs' Postgres role.
    - The Firecrawl key is a Unity Catalog secret readable only by the jobs' service principal.

## Databricks products by step

| Step | Runs on |
| --- | --- |
| Contract, prepare, enrich, load, publish, recapture | Lakeflow Jobs, serverless (`JOBS`), `STANDARD` performance target |
| Structuring and writing | Foundation Model APIs, pay-per-token (`MODEL_SERVING`) |
| Discovery, extraction, screenshots | Firecrawl (external, credits), via MCP over streamable HTTP |
| Canonical views, history, evidence index, approved table | Unity Catalog + Delta |
| Screenshots and crops | Unity Catalog Volumes |
| Catalog in Postgres | Lakebase synced table (`LAKEFLOW_CONNECT` / `DLT`, snapshot) |
| Results, reviews, edits, settings, audit | Lakebase Postgres (`LAKEBASE`), scale to zero after 30 min |
| Review app | Databricks Apps (`APPS`) |

## Tables in Unity Catalog

**Sources (read only):**
- the retailer's tables;
- the three canonical views built over them.

**Normalized by `prepare`:**
- `product_input`: active products (GTIN as `ean`, `product_id`, title, alternative title, brand, supplier,
  department, category and subcategory ids and names).
- `attribute_definition`: attributes per subcategory, with required flag, description, value type, unit, role and
  `allows_free_text`.
- `attribute_allowed_value`: active vocabulary options.

**Written by the enrichment** (append-only, with `run_id`):
- `enrichment_run`: run metadata, model, prompt version, settings snapshot, counts and status.
- `product_enrichment`: generated content, quality metrics, `content_language`, `content_profile`, `settings_hash`.
- `product_fact`: atomic values with URLs, excerpts, source tier and confidence.
- `product_attribute`: normalized attributes, applicability and vocabulary mapping, with `rejection_code` and
  `applicability_code`.
- `product_attribute_evidence`: visual evidence links per run, GTIN and attribute, with coordinates, Volume paths and
  hashes.
- `validation_issue`: rule errors and warnings, with `params_json`.
- `contract_check`: results of the source-contract checks.

**Read views:**
- `product_catalog`: product detail with the latest result;
- `enrichment_summary`: the latest result of each enriched product.

**Destination:** the approved-products table (`destination_*`), written only by the publish job.

## Tables in Lakebase

**Synced from Delta:**
- `brickfill_serving.products`: a snapshot of `v_products`, keyed by `product_id`.

**Loaded by the enrichment** (`load_lakebase` task, schema `enrichment`):
- Only the latest run of each product is kept. The marker is written last; superseded runs are removed afterwards.
- `product_enrichment`: one row per enriched product. `product_attribute`, `product_fact` and `validation_issue`
  hold that run's children, keyed by `(ean, run_id, row_id)`.

**Created and written by the app** (`brickfill_app`):
- `product_review`: review status (`PENDING`, `IN_REVIEW`, `APPROVED`, `REJECTED`), assignee, notes and the
  enrichment run the decision was made on (`run_id`). It is the review queue that sizes the daily batch.
- `attribute_override`: edited values with reason and author. At most one active edit per product and attribute;
  earlier ones become inactive, for history.
- `attribute_evidence`: manual evidence linked to an edit, or to the AI value of one run (`run_id`). Removal is
  logical; files are never deleted.
- `audit_event`: append-only history of every product change, with the user's e-mail (`actor`) and Databricks id
  (`actor_id`).
- `app_settings`, `category_settings`: enrichment settings (global and per scope), versioned.
- `settings_event`: append-only history of every settings change.

Delta is the system of record for the AI output: history, analytics and the evidence index. The app computes the
effective view by applying the latest active edit over the immutable AI result.

## Source policy

- **Source tiers:** `official`, `authorized_distributor`, `recognized_retailer` and `other`.
- **Conflicts:** the official source wins. Without one, the value is omitted and the conflict recorded.
- **FAQ:** answers require official evidence.
- **Published values:** every published value has at least one citation of a page extracted by Firecrawl.
  Otherwise the value is null and a validation issue is created.
- **Vocabulary:** values with a vocabulary are accepted only when they match an existing option.
  - **Exact match:** accepted as is.
  - **Spelling-only match:** accepted with status `APPROVED_ALIAS`. These count as the same option:
    - the same number and unit, with decimal comma or point and unit names from the locale packs: `6,7"` = `6.7"` =
      `6.7 inches`, and `16.44 cm` = `16.44` in an attribute whose `unit` is `cm`;
    - the same text without spaces, hyphens or a trailing `.0`: `06868-24-00953` = `068682400953`, and
      `Android 14.0` = `Android 14`;
    - the same text without a trailing parenthesized detail: `FHD+ (1080x2400)` = `FHD+`.
  - **Rejected:** different numbers (`14.4` ≠ `14.467`), thousand separators (`1,000` ≠ `1`) and semantic
    approximations.

  The published value is always the vocabulary option.

## Visual evidence

HTML extractions return, in the same Firecrawl session, the text (markdown and raw HTML), the full-page screenshot
and the coordinates of the visible text (a DOM map returned by `executeJavascript`).

**Before the screenshot**, the scripts in `src/brickfill/capture_scripts/` act like a visitor would. Nothing is
forced visible with CSS. The scripts:
- decline the cookie banner;
- open `<details>`, `aria-expanded` accordions and "show more" buttons, in English, Portuguese and Spanish;
- scroll the page to load lazy content.

**Focused capture.** Values present in the page text but without a crop get a second extraction of the page.
- For each value, `reveal.js` clicks the page's own control that opens the section or tab, centers the value and
  takes a viewport screenshot between two text maps.
- The window is not resized, so image and coordinates describe the same layout.
- When the value still doesn't show, the evidence gets `NOT_VISIBLE`, with the reason.

**Crop validity.**
- The text, positions and width of the two maps, before and after the screenshot, must match. The final height and
  viewport width must match the image pixels.
- The crop is derived only when the verbatim excerpt and the fact value identify a unique region.
- Capture failures don't invalidate the text extraction, but require review of the value.
- PDFs keep the text extraction but are never presented as visually proven.

**Archiving.** Files and links are written before the `product_enrichment` marker. There is no automatic deletion and
no overwrite of history.

**In the app.** The app only reads the evidence Volume, through the `/api/files/evidence/*` route, which is confined
to that Volume.

**Recapture** (**Evidence recapture** job):
- recaptures screenshots and crops for one GTIN and up to three attributes of its latest result;
- doesn't redo the AI research or change the published result;
- has its own credit cap (`max_credits`) and never repeats paid calls.
